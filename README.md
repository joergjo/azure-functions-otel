# Azure Functions + OpenTelemetry Sample

This sample demonstrates OpenTelemetry auto-instrumentation and manual
instrumentation in an Azure Functions Node.js/TypeScript application using the
v4 programming model. HTTP and Event Hubs functions export traces, metrics, and
logs over OTLP through an OpenTelemetry Collector. Redis provides shared state
and deliberate failure injection.

The instrumentation bootstrap follows the general OpenTelemetry guidance for
Node.js applications rather than the outdated Azure Functions-specific
OpenTelemetry guidance.

The sample supports:

- A fully local observability stack based on Grafana's OpenTelemetry LGTM image
- A local OpenTelemetry Collector that exports to Azure Monitor Application
  Insights
- Azure deployment using either Bicep or Terraform

## Architecture

The Function App sends OTLP/gRPC telemetry to a collector:

```text
Azure Functions -> OpenTelemetry Collector -> Grafana LGTM (local)
                                      \----> Azure Monitor Application Insights
```

The selected Docker Compose file determines the local destination. Azure
deployments run the collector on Azure App Service and export to the Azure
Monitor OTLP ingestion endpoints generated by Application Insights.

## Limitations

2. The deployed infrastructure does not use private endpoints for every
   resource. Event Hubs, Azure Managed Redis, and collector configuration
   storage are publicly reachable. TODO: Add private endpoints
3. The sample has no demo client that starts a trace before invoking a function.
   For HTTP functions, a tool such as
   [otel-cli](https://github.com/equinix-labs/otel-cli) can provide that parent
   trace. TODO: Add a Kafka/EventHub client app that emits OpenTelemetry
4. Deployment helpers are Bash scripts. On Windows, use WSL2. TODO: Create PowerShell versions of the Bash scripts.
5. The OpenTelemetry Collector always uses a service principal to authorize its access to the OTLP endpoint. TODO: For Azure Deployments, use the system-assigned managed identity of the App Service.

## Prerequisites

### Local execution

- Node.js 24 LTS and npm 11
- [Azure Functions Core Tools v4](https://learn.microsoft.com/azure/azure-functions/functions-run-local)
- Docker Desktop or another Docker Compose-compatible runtime
- Access to Azure Event Hubs
- Bash on macOS or Linux, or WSL2 on Windows

### Azure deployment

- [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli)
- An Azure subscription and permission to create resources and role assignments
- `jq` for the service-principal helper
- Bicep through the Azure CLI, or Terraform 1.9 or later
- `curl` and Python 3 when using the Terraform deployment helper

## Configure the Function App Locally

Copy the settings template:

```bash
cp local.settings.template.json local.settings.json
```

Set these values in `local.settings.json`:

| Setting | Local value |
| ------- | ----------- |
| `EventHubConnectionString` | Event Hubs **namespace** connection string without `EntityPath` |
| `EventHubName` | Name of an existing hub, such as `debug` |
| `ConsumerGroup` | `$Default` or `blue` to process messages; other values intentionally discard them |
| `RedisConnectionString` | `redis://localhost:6379` |
| `RedisPassword` | Empty for the local Redis container |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4317` |
| `OTEL_SERVICE_NAME` | Service name shown in telemetry, such as `demo-function-app` |

> [!IMPORTANT]
> The Event Hubs connection string is namespace-scoped. `EventHubName` selects
> the entity separately, so do not add `EntityPath`.

Once the Azure infrastructure has been deployed, it is also possible to use the OpenTelemetry Collector and Redis in Azure for local execution.

## Choose a Local Observability Mode

The two Compose files are alternatives. Both start Redis and Azurite, but they
send telemetry to different destinations.

### Option A: Local Grafana OpenTelemetry LGTM stack

`compose.lgtm.yaml` starts Grafana's [all-in-one OpenTelemetry LGTM image](https://grafana.com/docs/opentelemetry/docker-lgtm/). It includes an OpenTelemetry Collector and local backends for traces, metrics, and logs. This
mode does not require Azure Monitor credentials or ingestion endpoints.

```bash
docker compose -f compose.lgtm.yaml up -d
docker compose -f compose.lgtm.yaml ps
```

Open Grafana at <http://localhost:3000>.

Stop the stack with:

```bash
docker compose -f compose.lgtm.yaml down
```

### Option B: Local collector exporting to Azure Monitor

`compose.yaml` starts only Redis, Azurite, and the OpenTelemetry Collector. The
collector uses `config/collector.yaml` and forwards traces, metrics, and logs to
the Azure Monitor OTLP endpoints associated with Application Insights.

Export the collector service-principal credentials and ingestion endpoints:

```bash
export CLIENT_ID="<service-principal-client-id>"
export CLIENT_SECRET="<service-principal-client-secret>"
export TENANT_ID="<azure-tenant-id>"
export TRACES_ENDPOINT="<azure-monitor-otlp-traces-endpoint>"
export LOGS_ENDPOINT="<azure-monitor-otlp-logs-endpoint>"
export METRICS_ENDPOINT="<azure-monitor-otlp-metrics-endpoint>"

docker compose up -d
docker compose ps
```

The deployment scripts print the three endpoint exports after provisioning
Application Insights. Store local credentials in `.env`, `.envrc` or another ignored
file, never in source control.

Stop the stack with:

```bash
docker compose down
```

## Run the Function App

Install dependencies, build, and start the Functions host:

```bash
npm install
npm run build
npm start
```

`npm start` runs a clean build before starting Azure Functions Core Tools.
During development, use `npm run watch` for continuous TypeScript compilation.

## Function Endpoints

All HTTP functions use anonymous authorization. With the local host running on
port 7071:

| Method | Local endpoint | Behavior |
| ------ | -------------- | -------- |
| `GET` | `http://localhost:7071/api/about` | Returns `redisReady` and the configured `consumerGroup` |
| `GET` | `http://localhost:7071/api/incr` | Increments `incr.count` in Redis and returns the new `count`; returns `503` when Redis is unavailable |
| `POST` | `http://localhost:7071/api/fail` | Stores the request body in Redis under `fail`; an empty body stores `off` |

For a deployed app, replace `http://localhost:7071` with the Function App
endpoint printed by the deployment script:

```text
https://<function-app-host>/api/about
https://<function-app-host>/api/incr
https://<function-app-host>/api/fail
```

Setting the failure flag to `on` causes the Event Hubs handler to record the
failure and intentionally terminate the worker after the next message:

```bash
curl -X POST http://localhost:7071/api/fail --data 'on'
curl -X POST http://localhost:7071/api/fail --data 'off'
```

The Event Hubs-triggered `messageHandler` function is not an HTTP endpoint. It
consumes from the hub named by `EventHubName`, using the consumer group named by
`ConsumerGroup`.

## Deploy to Azure

Bicep and Terraform are parallel deployment options. Use one implementation for
a given resource group; their generated resource names and state are not
interchangeable.

Both options create:

- Log Analytics, Azure Monitor workspace, and Application Insights
- Event Hubs namespace and a hub named `test`
- Azure Managed Redis
- Storage for the deployed collector configuration
- OpenTelemetry Collector on Azure App Service
- Flex Consumption Function App and its managed identity and role assignments

The service principal used by the collector must exist before either
deployment.

### 1. Create the collector service principal

Sign in to Azure and run:

```bash
az login
./create-sp.sh
```

An optional argument changes the default service-principal name:

```bash
./create-sp.sh my-collector-sp
```

Export the `CLIENT_ID`, `CLIENT_SECRET`, and `TENANT_ID` values printed by the
script. A manually created service principal works as long as the same
environment variables are set.

### 2A. Deploy with Bicep

```bash
export FUNCTIONS_RESOURCE_GROUP_NAME="functions-otel-dev"
./deploy.sh
```

`deploy.sh` creates the resource group, deploys `infra/bicep/main.bicep`, and
grants the collector service principal **Monitoring Metrics Publisher** on the
Data Collection Rule generated by Application Insights.

### 2B. Deploy with Terraform

```bash
export FUNCTIONS_RESOURCE_GROUP_NAME="functions-otel-dev"
./deploy-terraform.sh
```

`deploy-terraform.sh` initializes `infra/terraform`, creates or imports the
resource group, validates and applies the configuration, and manages the
collector's Data Collection Rule role assignment. It uses local Terraform state
and a saved plan during deployment. State and variable files are ignored
because they can contain secrets; `infra/terraform/.terraform.lock.hcl` is
version-controlled for reproducible provider selection.

Both deployment scripts support these optional environment variables:

| Variable | Default | Purpose |
| -------- | ------- | ------- |
| `FUNCTIONS_RUNTIME` | `node` | Function App runtime |
| `FUNCTIONS_RUNTIME_VERSION` | `24` | Runtime version |
| `EVENTHUB_LOCATION` | `swedencentral` | Resource group and resource location |

On success, each script prints the Function App endpoint, Event Hubs namespace
endpoint, Azure Monitor OTLP ingestion endpoint exports, and the
`func azure functionapp publish` command needed to publish the application
code. Terraform also prints the collector endpoint.

> [!NOTE] The health check performend by `func azure functionapp publish` sometimes fails even though the application works correctly.

### Destroy a Terraform deployment

Use the guarded destroy script rather than running `terraform destroy`
directly:

```bash
export FUNCTIONS_RESOURCE_GROUP_NAME="functions-otel-dev"
./destroy-terraform.sh
```

The script requires the existing local `infra/terraform/terraform.tfstate`,
checks that the state, resource group, subscription, and tenant agree, and asks
you to type the exact resource-group name. It destroys Terraform-managed child
resources while preserving the resource-group container.
